# 开发与项目协作流程

本文件只在新增或修改页面、执行开发验证、维护 Dashi 或准备阶段汇报时按需阅读。

## 页面确认

任何影响用户可见页面的新增或修改，必须先完成以下步骤：

1. 说明涉及的页面、路由和改动目的。
2. 提交文字草图，包括页面自上而下的区域、主要内容、主操作、次操作和跳转关系。
3. 明确本轮不改的部分，防止范围扩散。
4. 等待用户明确确认或提出修改。
5. 用户确认后立即开发，并完成最低必要验证；不再要求用户审阅正式规格或实施计划。

纯文档、测试脚本、构建配置和不影响页面呈现的修复无需文字草图。

默认禁止把小型静态页面开发扩展成“文字草图 → 正式设计规格 → 再次确认 → 正式实施计划 → 开发”的多重门禁。开发前如需安排步骤，只在当前会话维护简短内部清单，不单独创建规格或计划文件，也不因此暂停等待用户再次确认。

只有出现以下情况之一，才单独编写设计规格或实施计划：

- 一次改动跨越多个独立业务链路或多个子系统；
- 存在会显著改变产品方向、数据结构或既有页面体系的方案选择；
- 用户明确要求输出设计规格、实施计划或分阶段方案。

## 轻量开发流程

按可独立讲解和验收的业务链路开发，不按孤立页面堆数量：

1. 确定本轮演示主题以及入口、列表、详情、确认和结果页面。
2. 草图确认后立即准备一致的 Mock 数据并修改页面，串通主按钮和返回路径。
3. 优先完成业务链路和页面展示，再做必要抽象；不为未来能力提前建设复杂架构。
4. 执行一次必要的相关测试、静态资源检查和生产构建；发现实际错误后再增加针对性检查。
5. 交由用户进行页面视觉、内容和业务演示验收。
6. 用户验收后创建本地提交，并同步任务与当前状态。

未经用户主动要求，不调用独立审查代理或额外代码审查任务；不为同一小型改动编写独立设计规格或实施计划，不重复请求草图确认，不重复执行多档浏览器检查、全量测试或多次过程同步。

## 代码与数据约定

- 页面放在 `src/pages/`，可复用布局和组件放在 `src/layouts/`、`src/components/`。
- 多页面共用数据放在 `src/data/`；小型一次性展示数据可以留在页面内。
- 异步数据和未来真实接口入口放在 `src/services/`。
- 新样式优先沿用所属页面族前缀，例如 `tp-`、`home-`、`finance-`、`ops-`、`ds-`、`m-`。
- 优先复用现有布局、按钮、卡片、标题和状态样式；修改哪个页面，只整理附近代码。
- 不强制 TypeScript、测试覆盖率、复杂状态管理或统一重写旧代码。
- 静态图片保存到本地项目资源，不依赖临时外链。

## PC 与易用性基线

重点检查 1920×1080、1600×900、1440×900、1366×768，兼顾 1280×720。

- 首页、列表页、工作台和确认页的核心任务尽量在首屏完成；详情、新闻、政策等长内容允许纵向滚动，但标题、核心数据和主操作应在首屏。
- 禁止整页横向滚动和用 `transform: scale()` 压缩整个页面；复杂表格、地图可以在自身区域滚动。
- 高度不足时优先隐藏或折叠装饰、推荐位和次要说明，不缩小关键文字和按钮。
- 正文通常不低于 16px；关键操作使用带完整动词的大按钮，少用只有图标的关键操作。
- 单页突出一个主要任务；表单字段尽量少，提供默认值、示例和清晰单位。
- 状态同时使用文字和颜色表达，保留清晰导航、面包屑、返回和下一步入口。
- 延续白底、深蓝文字、主题蓝按钮和轻边框卡片风格，桌面端可沿用最大 1516px 内容容器。

## Mock 数据与外部资料

- 演示数字可以使用 Mock 数据，但不能伪装成真实实时数据。
- 政策优先引用原始发布机关页面，记录发布单位、日期、文号和链接。
- 新闻记录标题、来源、发布时间、摘要和原文链接。
- 行情记录地区、品类、规格、单位和采集时间。
- 公众号和自媒体只作为线索；正式展示前尽量找到原始或权威来源。
- 不整篇复制新闻，不使用来源不明图片；联网资料与本地 Mock 数据分开维护。

## 每轮最低验证

- 相关测试通过。
- 关键路由、按钮跳转和返回路径可用。
- 涉及页面无明显溢出、遮挡或整页横向滚动。
- 本地静态资源检查通过。
- `pnpm build` 成功。

## Dashi 与当前状态

- 只使用项目 `salmon-digital-platform`，不得与其他项目混用。
- 任务按可独立验收的阶段或业务链路拆分；不为单个静态页面或很小文案调整创建任务。
- 开始任务前读取最新任务内容和评论；执行中只在范围变化、关键决定、明确阻塞或完成交付时留评论。
- 完成自检和下述固定收尾门禁后才能移至 `in_review`；只有用户明确验收且再次核对门禁后才能标记 `done`。
- `docs/CURRENT_STATE.md` 是全项目当前进度的唯一恢复入口。任务开始、进入 `in_review`、用户验收为 `done`、阻塞或取消时同步更新。
- `CURRENT_STATE.md` 只保存当前事实；历史任务细节留在 Dashi 评论，方向性变化写入 `docs/CHANGELOG.md`。
- Dashi 状态、`CURRENT_STATE.md` 和本地 Git 提交必须一致。

### 固定收尾门禁

每个任务在请求验收和最终关闭前都必须逐项核对，不能依赖后续任务集中补写：

1. **Dashi 与当前状态（每次必做）**：读取任务最新正文、评论和版本；同步 Dashi 评论、任务状态与 `docs/CURRENT_STATE.md` 中的当前阶段、实现事实、验证结果和下一步。
2. **页面与链路（按变更必做）**：只要新增、删除或改变页面、路由、导航入口、按钮跳转或业务链路，就同步 `docs/PAGES_AND_FLOWS.md`；已交付内容必须从“待建设”迁入“当前已有”，不得只记录在 `CURRENT_STATE.md` 或 Dashi。
3. **需求范围（按变更必做）**：新增、取消或调整功能范围、阶段边界和验收口径时，同步 `docs/REQUIREMENTS.md`。
4. **方向与长期规则（按变更必做）**：产品方向、文档职责、开发门禁或长期协作规则变化时，同步 `docs/CHANGELOG.md`；常驻硬规则同时更新根目录 `AGENTS.md`，详细执行步骤归入本文件。
5. **入口资料（确有变化才做）**：运行命令、目录结构或文档入口变化时更新 `README.md`；项目定位、用户变化时更新 `PROJECT_OVERVIEW.md`；UI/PPT 资料或使用规则变化时更新 `UI_REFERENCE.md`。没有对应变化时不得为了形式重复改写。

固定执行顺序：

1. 重新读取 Dashi 最新状态和 `git status --short`，识别并行会话文件，禁止覆盖或混入其他任务改动。
2. 根据本轮实际差异完成上述文档映射；对照路由配置、页面文件和任务验收记录，删除已经过期的“待建设”“下一步”和旧状态描述。
3. 执行相关测试、静态资源检查、生产构建和 `git diff --check`；若全量测试受其他并行任务的已确认红灯影响，必须运行本任务相关测试并在 Dashi 结论中准确披露全量结果与归属。
4. 只暂存并提交当前任务文件；提交后核对提交文件清单，再写 Dashi 结论并变更状态。
5. 最后重新读取 Dashi、`docs/CURRENT_STATE.md` 和本地提交，确认三者一致。任何一项未完成或不一致，任务必须保持原状态，不得进入 `in_review` 或 `done`。

任务进入 `in_review` 前添加一条简短结论，固定包含：

```text
结论：任务已完成自检，进入待验收。
实际完成：列出主要交付，不超过 4 项。
验证结果：列出测试、构建和关键页面检查。
文档同步：列出本轮已同步的文档；按变更判断不适用的文档必须写明“不适用”及原因。
注意事项/未完成：只列仍然有效的限制；没有则写“无”。
本地提交：填写提交哈希；未提交时说明原因。
下一步：说明用户验收后或下一个任务要做什么。
```

## 简要汇报格式

1. **本轮完成**：完成了什么页面、文档或链路。
2. **验证结果**：构建、关键跳转或视觉检查结果。
3. **待确认/风险**：只列仍需用户决定或确实存在的问题；没有则写“无”。
4. **下一步**：建议继续处理的一项工作。
